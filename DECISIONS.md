### D-33: Candidate representation — title+subtitle is a v1 cost baseline, NOT the faithful default; full text is a toggle
**Flagged by Humzah as a serious methodological decision.** The ranker currently sees each candidate as ONE line — `[id] | publication | author | title | subtitle` (~40 tokens/post for Substack; for NBER the "subtitle" is the full abstract, ~300 tokens). The full essay body IS captured at ingest (`candidates.full_text`) but is not sent. A whole 180-post Substack run is ~13.7k tokens this way vs. ~1.05M tokens if the bodies were included (~75×).

**Why this is a real fidelity problem, not a wash:** Tyler Cowen's identity and reputation are built on reading enormous volumes fast and reading *most* of what crosses his desk — his picks reflect judgments made *after reading*, not after glancing at headlines. Predicting his taste from title+subtitle therefore measures "does this look MR-worthy at a glance," a strictly weaker proxy than "would Tyler link this having read it." It imposes a systematic ceiling: a bland-titled but Tyler-perfect essay is under-ranked by the models though Tyler would link it. So title-only under-represents his full sense of taste by construction.

**It is a toggle, and cheaply.** `full_text` already exists for Substack; feeding it is a prompt-construction change. Constraints that shape the *right* upgrade (rather than naive full-text):
- **Kimi K2.6 has a 262k context window** — a ~1.05M-token full-bodies prompt *exceeds it entirely*, so naive "send every full essay" is infeasible if we want all four models comparable.
- Cost jumps from ~$1/Substack run to ~$22/run (4 models) at full bodies; ~$5–7/run at truncated bodies.
- Options, cheapest-faithful first: (a) **truncated full text** (first ~1–1.5k words/post → ~200–360k tokens, fits all models, ~$5–7/run) — much closer to Tyler's actual read; (b) **two-stage triage→deep-read** (rank on title+subtitle, then re-rank the top ~20 on full text — cheapest way to get full text onto the contenders); (c) full bodies (infeasible for Kimi; expensive).
- NBER already sends the full abstract (the paper's natural decision surface; full PDF would be a further step).

**Versioning:** changing the candidate representation changes what every model sees and MUST bump `prompt_version` so title-only and full-text runs never blend in a leaderboard. Today's first live runs (both tracks) are the title+subtitle baseline (`prompt_version` v1.0).

**Resolved (Humzah, 2026-07-18): adopt truncated full text — option (a).** Every candidate now carries the first ~`candidate_body_words` (900) words of its actual body (HTML-stripped), no triage gate — faithful to "Tyler reads everything," fits Kimi's 262k window (~180 posts ≈ ~226k tokens), ~$5–7/Substack run. `prompt_version` bumped to **v2.0**; the ranker-instructions input-format description updated to match. The v1.0 title-only runs are retained as a baseline so we can *measure* how much reading the content moves each model's recall. (NBER already sent the full abstract, so its representation is materially unchanged across v1.0→v2.0.) Body word-budget lives in `config.yaml`; if a day's pool is large enough to threaten Kimi's window, lower it or drop the small-context model.

### D-29: Ground-truth scoring engine (`score.py`) — harvest, match, metrics

### D-27: NBER matching window calibrated to 14 days; classic-paper links out-of-scope
Measured Tyler's NBER link-lag empirically: fetched `citation_publication_date` for all 501 unique papers he linked since 2022-01 (via each paper page's Google-Scholar meta tag; 511 link events, 0 missing, 0 negative). Distribution is heavily front-loaded — **median lag 1 day, p75 3, p90 6, p95 10** — then flat: 7d captures 92.2% of links, 14d 97.1%, 21d 97.7%, and nothing new arrives between 21d and 90d. The p99 (1,585d) is a categorically different behavior: Tyler resurfacing *classic* papers (w6439 from 1998, w7639 from 2000), not fresh-pick prediction.

Decisions (both Humzah's editorial call): (1) **`nber.matching_window_days = 14`** (was provisional 21) — captures 97.1% with a lean ~80-candidate scoring window; going wider buys ≤0.6pp until the un-catchable classics. (2) **Classic-paper links (release > 14d before the link) are `out_of_scope`** — counted and logged, excluded from the NBER recall denominator, not scored as misses (~2–3% of links). (3) Operational consequence recorded: **NBER must be polled daily** (median lag = 1 day; weekly polling would ingest papers after Tyler links them). The 501 release dates are persisted in a new `nber_paper_dates` table (D-13 single-source-of-truth), doubling as backtest release-date backfill and the input to the fresh/out-of-scope split. Supersedes the provisional-21 open item flagged in D-25/D-24.

### D-25: `ingest.py` built source-type-pluggable; NBER track wired alongside Substack
Ingestion is a source-agnostic orchestrator over pluggable `SourceAdapter`s (`discover`/`fetch`/`parse`). The orchestrator saves each raw feed verbatim, dedups parsed records against `candidates.canonical_url` (UNIQUE), inserts new ones, counts per-feed failures, and marks a feed inactive after `inactive_after_consecutive_failures`. Two adapters ship: `SubstackAdapter` (time-windowed — keep entries within `ingest_lookback_hours`) and `NberAdapter` (dedup-driven — NBER's feed has no per-item dates, so every `/papers/w#####` item is a candidate and `published_at` = first-seen date). A third track (e.g. SSRN) is a new adapter class, not a refactor. Schema: a `track` column added to `publications`/`candidates`/`runs`/`predictions` (default `'substack'`, back-fills the 538 existing rows) keeps the two leaderboards from ever blending; a `consecutive_failures` counter added to `publications` implements the inactive-after-N rule (the brief's schema omitted it). NBER is seeded as a single `publications` row (`track='nber'`, `source='manual'`, `corpus_version='nber-v1.0'`). Live smoke test ingested 40 papers with clean canonical URLs; 17 new tests (parsing offline via fixtures + orchestration via a stub adapter), full suite 138 green. **Open:** NBER `matching_window_days` is a provisional 21 pending link-lag measurement; the raw feed gives no release dates so backtest will need a per-paper date backfill.

### D-24: Non-Substack sources (NBER, arXiv, SSRN, news) deferred to a possible corpus v2 — not in v1
The brief scopes corpus v1 to Substack publications only (§5.1, and §Guardrails: "Do not add publications to the corpus outside the defined derivation + manual file"). NBER (872 Tyler links since 2022-01), SSRN (376), and arXiv are his largest *scholarly* sources and are trivially pingable (NBER new-working-papers RSS; arXiv API/RSS per category) — so an expansion is technically easy and fits the D-21 wide-net spirit. Held out of v1 anyway, for reasons that are design, not laziness: (1) volume/cadence mismatch — arXiv floods hundreds of papers/day and NBER batches weekly, vs. a Substack's few posts/day; mixing them uncontrolled would swamp and dilute the daily candidate pool and distort recall. (2) Homogeneous candidate type keeps the ranking task well-defined and the metric interpretable. (3) Task-difficulty and base rates differ wildly between "which Substack" and "which NBER paper," so they must not blend into one number (cf. D-22). Crucially we lose nothing by waiting: ground truth already records Tyler's non-Substack picks as `out_of_corpus` (brief §5.5), so we can measure the *ceiling* of a paper-track expansion retrospectively before building any adapters. If pursued, v2 = per-source-type ingestion adapters + per-source volume caps/category filters + a taste-profile track for papers, reported as a **separate** track from Substacks. Design hook: build `ingest.py` source-type-pluggable from the start even though v1 only wires the Substack adapter. Editorial question raised by Humzah 2026-07-15.

### D-22: Report hit-rate split by "repeat MR favorite" vs. "long-tail" publication
To demonstrate the ranker exercises *taste* rather than a base-rate/popularity prior, every prediction is tagged by whether its source publication is a frequently-featured MR favorite or a long-tail source, and recall/MRR are reported separately for the two strata. The failure mode this guards against: a model that scores well only by re-picking authors Tyler already links often would look competent on a blended number while having learned nothing about *what makes a post MR-material*. Splitting the metric makes that shortcut visible. "Favorite vs. long-tail" is defined from archive link-frequency (exact cutoff TBD when we see the distribution); the tag lives on the prediction row so it can be recomputed under alternate cutoffs. Companion to D-21.

### D-21: Watchlist corpus deliberately kept wide (low inclusion threshold)
The publication watchlist casts a wide net on purpose. All direct `*.substack.com` hosts Tyler linked since 2022-01 are included regardless of link count; custom-domain hosts are probed at a low link threshold (≥2). Rationale is methodological, not incidental: a narrow corpus of Tyler's repeat-featured authors lets a model succeed via a base-rate shortcut ("this author gets linked a lot, bet again"), which measures popularity memory rather than taste. A broad, noisy corpus — where most posts on any given day are *not* MR-material — forces the model to apply Tyler's actual taste function to discriminate signal from noise. Breadth is the property that makes the eval discriminating. Note the ≥2 threshold on custom domains is a Substack-*detection* efficiency control (probing every 1-off custom host mostly yields non-Substacks the feed-fingerprint discards), not a taste filter; we can widen it further after inspecting the ≥2 yield. Editorial call by Humzah. Measured by D-22.

## 2026-07-12

### D-16: Substack-specific query params added to canonicalizer strip list
Empirical: on a June 2024 archive scrape of ~13 Substack URLs Tyler linked, five params kept showing up: `r` (subscriber referrer id), `triedRedirect` (internal redirect flag), `isFreemail` (display-mode hint), `post_id` and `publication_id` (both duplicate info already in the slug/host). None affect content identity. All added to `_TRACKING_PARAM_EXACT` in `normalize.py`. Cost of stripping is that some other site's legitimate `?r=` param would be collapsed — that risk is small compared to false non-matches on Substack, which is our whole eval target.

### D-15: Archive scraper rate = 4 req/sec (0.25s delay) with 429/503 backoff
Brief §5.1 suggested 1 req/sec. Bumped to 4 req/sec for the one-time archive backfill because MR is a well-provisioned hosted WordPress site behind a CDN and 4 req/sec is still an order of magnitude below what a real user's browser generates on a single pageview (dozens of image + JS + CSS loads in parallel). The scraper backs off on HTTP 429 (Too Many Requests) and 503 (Service Unavailable) with exponential delays (2s → 4s → 8s) so if MR ever pushes back we automatically slow down instead of getting blocked. Rate is a config value (`archive_scraper_delay_seconds` in `config.yaml`); dial back up if needed. Full backfill ETA ~30 min vs. ~75 min at the original 1 req/sec.

### D-14: Archive scrape resumability via committed checkpoint JSON
`data/archive_checkpoint.json` records which months are fully scraped. Committed to git so a fresh clone (or a laptop rebuild) can resume without re-fetching completed months. Not stored in the DB because it's simple key-value progress state, not analytical data, and a text file diffs cleanly.

### D-13: Extracted archive data stored in DB tables, not JSON files
Raw MR post HTML is gitignored under `data/raw/mr_archive/`; extracted structured data (post URL, title, publish date, ordered outbound links + canonical URL form) lives in two new tables — `archive_posts` and `archive_links` — inside `data/tyler.db` which is committed. Downstream consumers (watchlist builder, few-shot generator, ground-truth validator) then query the DB rather than parsing scattered JSON files. Single source of truth. Re-extraction from raw HTML is possible if we ever need to add fields.

### D-12: MIT license
Public repo intended to be shared and forked (Andy Hall at Stanford GSB, possible student collaborators). Permissive license removes friction.

### D-11: Query params sorted alphabetically in canonical URLs
So string-equality on canonical URLs works regardless of the order params arrive in. Non-tracking params are preserved (some Substack search/filter URLs use them) but order-normalized so `?a=1&b=2` and `?b=2&a=1` compare equal.

### D-10: `www.` subdomain stripped in canonical URLs
Virtually all modern sites serve `www.foo.com` and `foo.com` as the same resource. Stripping uniformly avoids false non-matches. If we ever meet a publication where the two differ, we add a per-publication exception rather than reversing this rule.

### D-09: Tracking parameters stripped from canonical URLs
Stripped: `utm_*`, `ref`, `ref_src`, `ref_url`, `source`, `fbclid`, `gclid`, `mc_cid`, `mc_eid`, `igshid`, `_hsenc`, `_hsmi`, `yclid`, `s` (twitter's `t.co` tracker). Everything else is preserved.

### D-08: `content_match` replaces the brief's `near_miss`
The brief reserved `near_miss` for embedding-similarity matching. We renamed to `content_match` in `ground_truth.match_type` because the semantic is "the linked article is the same underlying content, not a miss." It's genuinely a hit and should be counted as such (in the "generous recall" metric, reported alongside strict recall). Implementation deferred until after live pipeline is trusted; until then, strict recall == generous recall and this is flagged on the dashboard.

### D-07: `raw_store.py` abstraction for raw blobs
`data/raw/` is `.gitignored` today; blobs live locally and in GitHub Actions artifacts (default 90-day retention). `raw_store.py` provides a `LocalFSBackend` implementing a `RawStoreBackend` Protocol so an `S3Backend` or `GCSBackend` can be dropped in without touching call sites — matters if we ever host this or need a longer audit trail.

### D-06: RSS-based ground truth polling instead of fixed retry
Rather than fixed 16:30 UTC + retry at 18:00 UTC, the scoring workflow polls MR's RSS every `gt_poll_interval_minutes` (default 15) between `gt_poll_start_utc` and `gt_poll_end_utc` (defaults 15:00 – 22:00 UTC) and exits early on match. Idempotent. Simpler than standing up a webhook relay.

### D-02: Rank + score preserved, not binary
Ranker output stays as `(rank, score_0_100)` per candidate rather than binary "included / excluded." Motivation: rank enables MRR and recall@K at multiple K, which distinguishes "confidently correct" from "included in a wide bucket." If models turn out to rank uselessly in practice (e.g., pure recency ordering), we can fall back to binary and note it in METHODOLOGY.

### D-01: Cross-day rank aggregation = best
When a candidate is ranked on multiple days in the trailing matching window and Tyler links it, the model's effective rank is the **lowest (best) rank across those days**. Rewards the model for ever having believed in the pick. Config value (`cross_day_rank_aggregation: best`); the DB always retains per-day ranks so metrics can be recomputed under alternate rules.
